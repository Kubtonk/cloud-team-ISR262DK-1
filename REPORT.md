###Ответы на Контрольные вопросы
1. Для чего в командном GitHub-проекте используются Issues?
Issues используются для трекинга (отслеживания) задач, багов, новых идей и предложений. Они позволяют команде структурировать работу: назначать исполнителей (Assignees), вести обсуждение проблемы до написания кода и привязывать конкретные задачи к этапам разработки.

2. Почему изменения рекомендуется выполнять в отдельной ветви, а не напрямую в main?
Ветвь main должна содержать только стабильную и рабочую версию проекта. Написание кода напрямую в main несколькими разработчиками неизбежно ведет к жестким конфликтам слияния (merge conflicts) и риску сломать проект. Отдельная ветвь дает возможность безопасно экспериментировать изолированно от других.

3. Что такое Pull Request и какую роль он выполняет в процессе командной разработки?
Pull Request (PR) — это формальный запрос на добавление изменений из рабочей ветви в целевую (в main). PR выполняет роль платформы для обсуждения кода: команда может посмотреть разницу файлов (diff), оставить комментарии, выявить ошибки и убедиться, что всё корректно, прежде чем код станет частью основной базы.

4. Чем отличаются действия Comment, Approve и Request changes при проверке Pull Request?

    Comment (Комментарий): Просто заметки, вопросы или предложения. Слияние (merge) при этом не блокируется.

    Approve (Одобрить): Подтверждение от проверяющего, что код написан качественно, ошибок нет, и он готов к безопасному слиянию.

    Request changes (Запросить изменения): Указание на критичные ошибки. Это действие жестко блокирует слияние (merge) до тех пор, пока автор не внесет правки, а проверяющий не снимет блокировку, изменив решение на Approve.

5. Как связаны Issue, ветвь, commit, Pull Request и merge в едином рабочем процессе?
Эти элементы образуют единый жизненный цикл выполнения любой задачи:

    Создается Issue (постановка задачи).

    На основе Issue разработчик создает ветвь (изолированная среда).

    Разработчик пишет код и сохраняет его с помощью commit (фиксация изменений).

    Завершенная работа отправляется на проверку через Pull Request.

    После успешного ревью происходит merge (слияние ветви с main), после чего изначальный Issue автоматически закрывается.
